# Fahrklar — first full audit (2026-09-12)

Scope: backlog #2. Covers contrast, keyboard/screen-reader, 390 px, and data
honesty across `/`, `/berater`, `/datenschutz`, `/impressum` on the
`smard-redesign` branch, against the light/blue theme and the new
`ControlBar`. `ControlBar.tsx`'s accessible names and `aria-expanded` were
already checked by hand (per the task brief) and are not re-litigated here.

Method: contrast ratios below are computed, not eyeballed, with a small
WCAG relative-luminance script run against every token in
`app/globals.css` plus the hardcoded colors found in `GermanyMap.tsx`
(script kept at the end of this run in the session scratchpad, not checked
into the repo — reproducible from the hex values quoted in each finding).
390 px checks used a real Chromium viewport at 390×844 against the live dev
server, reading actual `getBoundingClientRect()` sizes, not the rendered
CSS.

**A note on timing.** Five other agents were editing the tree live during
this audit, and it moved more than a "note and move on" drive-by — by the
end of this pass, `app/globals.css`, `SiteHeader.tsx`, `SiteFooter.tsx`,
`ResultView.tsx`, `data/*.json`, `lib/copy.ts`, `lib/engine/{charge,evaluate,types}.ts`
had all changed since I first read them, and a new `components/ui/RangeBar.tsx`
appeared. Where a landed change directly fixed or contradicted a finding
below, I re-checked it against the current file and say so inline, dated
to this session rather than to a git commit (little of this was committed
at time of writing — see backlog rule 3). Anything not called out as
re-checked reflects the state at first read and may already be stale;
that's the nature of auditing a tree five other people are actively
rewriting.

## 1. Contrast

**1.1 — The "this value was assumed" marker fails contrast — the app's central claim is hard to read.**
`--color-assumed: #83888f` is used as the *only* visual signal that a value
came from the engine's guess, not the reader's input (CLAUDE.md rule 2:
"An assumed value is marked where it can be corrected"). Measured:

- `#83888f` on `#ffffff` (surface) → **3.57:1**
- `#83888f` on `#f4f4f2` (canvas) → **3.24:1**

Both are small text (`text-sm`/`text-xs`, not 18px+/14px-bold), so WCAG AA
needs 4.5:1. This fails at both sites it's used:
- `components/advisor/ControlBar.tsx:75` — the italic value inside every
  "Nutzung: *Alltag*" style control, exactly where a reader is supposed to
  notice "this was guessed, fix it if wrong."
- `components/advisor/ResultView.tsx:162` — "Teurer Ausreißer (Budget
  offen)" on a car card.

Should be: darken `--color-assumed` until it clears 4.5:1 on white (needs
roughly `#5f646b` or darker), or stop relying on color alone and add a
non-color cue (icon, underline) as backup — color contrast failure is worse
here than almost anywhere else in the app because the *entire product
promise* is "we tell you what we don't know," and this is the one pixel
that says so.

**1.2 — `GermanyMap.tsx` was never migrated off the old dark theme; its stop labels can go invisible.**
`components/showroom/GermanyMap.tsx` draws the country outline, route line
and stop markers with hardcoded hex literals, not theme tokens — they were
never touched by the light-theme remap:

- polygon fill `#1f2225`, stroke `#3a3e42` (lines 110–115)
- route/corridor stroke `#d4a84b` — the *old dark-theme gold*, not the new
  blue accent (lines 116–135)
- stop circle fill `#1a1c1e`, stop-time text fill `#ebe6dc` (lines 136–156)

Visually confirmed live (390 px and desktop, `/berater` with a trip
active): the map renders as a near-black silhouette with an amber route
inside an otherwise white, blue-accented card — it reads as a leftover
fragment of the old theme, not a redesign miss you'd catch by scanning
class names, because none of this is a Tailwind token.

Worse than the visual clash: the stop-time label (`#ebe6dc`, near-white) is
only legible because it happens to sit on the dark landmass polygon.
Measured:
- `#ebe6dc` on `#1f2225` (on the landmass) → 12.85:1, fine
- `#ebe6dc` on `#ffffff` (off the landmass, i.e. on the card background) → **1.24:1**

`OUTLINE` (line 29) is explicitly "coarse," and stop points are placed by
projecting real lat/lng onto it — a stop near a border or coastline (or any
route that runs close to the simplified edge) will place its near-white
label directly on the white card, effectively invisible. This isn't
hypothetical: three of the seeded routes hug the western and northern
edges of the simplified outline. Should be: move these to theme tokens
(`--color-ink`/`--color-accent` family) so a future theme change can't
strand them again, and give the text a fill that works regardless of what
it sits on (e.g., a small opaque pill behind each label, or `paint-order`
stroke in the card background color).

**1.3 — Unselected chips and every text input are nearly invisible against the page — a UI-component contrast failure, not just a hairline aesthetic.**
Measured (WCAG 1.4.11 non-text contrast wants 3:1 for a control's visual
boundary):

- fill `--color-surface` (`#ffffff`) on `--color-canvas` (`#f4f4f2`) → **1.10:1**
- border `--color-line` (`#d8d9dd`) on `#ffffff` → **1.41:1**
- border `--color-line` on `#f4f4f2` → **1.28:1**
- `--color-line-strong` (`#b7babf`) on either → **1.77–1.95:1**

This is the fill+border combination used by every unselected chip
(`components/ui/ChipGroup.tsx:31-34, 83-87, 96-102`) and every text input
(`inputClass`, `ChipGroup.tsx:131-132`), sitting directly on `bg-canvas`
with no intervening panel. Confirmed on screen (desktop, `/berater`): the
"Alltag / Familie / Lange Autobahnfahrten / Alles etwas" chip row shows
almost no visible pill outline — the buttons read as floating text until
hovered or focused. This is systemic (it's the intake form's primary
interaction surface, not an edge case) and is worse than a typical subtle-UI
choice because at these ratios the boundary is not just quiet, it is below
the threshold most people can reliably perceive. Should be: raise
`--color-line` toward `--color-line-strong` or darker, or give unselected
chips a filled `--color-sunken` background so the shape is legible without
depending on the 1.1–1.4:1 border.

**1.4 — Leftover token inconsistency inside a single file.**
`components/ui/ChipGroup.tsx`'s `MultiChipGroup` "unknown" button (lines
96–102) is styled with the *old* `gold`/`graphite`/`paper` alias set
(`border-gold bg-gold text-graphite` / `border-graphite-line
bg-graphite-card text-paper`), while every other button in the same file
and the same component uses the new semantic set (`border-accent bg-accent
text-white` / `border-line bg-surface text-ink`, lines 31-34, 83-87). Both
resolve to visually similar colors today (gold and accent are the same
blue), so nothing is *broken* yet, but it means the alias cleanup called
for in `globals.css`'s own comment ("remove an alias once its last caller
is gone") is incomplete, and the two systems will drift the next time
either token is changed independently. Low urgency, but exactly the kind of
seam the task asked to hunt for. Same pattern in
`components/advisor/QuestionForm.tsx:97-101`.

**1.5 — Confirmed non-issue: `--color-accent-band` is not used as text anywhere.**
Grepped every `text-*`/`className` use of `accent-band` across `app/` and
`components/` — none found. It (and `--color-data-range`, the same hex
`#2b7fc0`) was defined but unconsumed at the start of this audit, which
lined up with backlog #5/#7 (range bars) being open. For the record, if it
is ever used as text: `#2b7fc0` on white is 4.29:1 and on canvas is 3.89:1
— large-text-only, fails as body text, exactly as the brief warned.

*Update, same session:* `design-system` landed `components/ui/RangeBar.tsx`
partway through this audit — a pure, engine-free bar primitive for backlog
#5/#7, not yet imported anywhere (grepped; no consumer yet, so nothing
user-facing changes from this finding today). It's worth recording because
it gets the exact pitfall above right on purpose: its own code comment and
a new block in `globals.css` (next to the `data-*` tokens) independently
derive the same numbers this audit did —
`--color-data-range` on `--color-data-track` is 3.40:1 (clears 1.4.11's
3:1) and 4.29:1 on white; `--color-data-range-soft` on track is only
1.13:1 and is used as a fill only, with the 3.40:1 border carrying the
actual boundary, which is the standard WCAG 1.4.11 technique for a fill
that can't clear contrast on its own. `--color-data-mark` clears 14–18:1
either way. I re-derived all four independently and got the same figures.
No action needed here; noted so whoever wires `RangeBar` into `ResultView`
next knows the contrast homework is already done.

**1.6 — Minor: catalog color swatches can be invisible, though they're decorative.**
`components/advisor/ResultView.tsx:151-155` draws a `12px` `aria-hidden`
dot in each car's `colorHex`. Several catalog colors sit very close to
white (`tesla-m3`: `#C0C0C0` → 1.82:1 on white; `hyundai-ioniq5`:
`#E8D5A3` → 1.31:1 on white), so the dot is nearly invisible on the card.
Not a WCAG violation (decorative, `aria-hidden`, not the only way to
distinguish cars), but if this dot is ever relied on for anything, it will
fail immediately.

## 2. Keyboard and screen reader

**2.1 — Invalid ARIA: a lone `role="radio"` with no `radiogroup`.**
`components/advisor/QuestionForm.tsx:92-104` — the "Weiß ich nicht" toggle
next to the day-distance field is a `<button role="radio"
aria-checked={draft.dayUnknown}>` with no `role="radiogroup"` ancestor and
no sibling radios. Per the ARIA spec a `radio` must live inside a
`radiogroup` (or be owned by one via `aria-owns`); a standalone radio is
undefined behavior for assistive tech — some screen readers announce it as
"1 of 1," others drop the checked state entirely. The equivalent "unknown"
toggle for body style, right below it in the same file
(`MultiChipGroup`'s unknown button, `components/ui/ChipGroup.tsx:93-106`),
correctly uses `aria-pressed` instead — that's the right pattern here too.
Fix: drop `role="radio"`/`aria-checked`, use `aria-pressed={draft.dayUnknown}`
like its sibling.

**2.2 — `ControlBar`'s disclosure doesn't return focus after Escape.**
`components/advisor/ControlBar.tsx:46-60` (the `Control` component) closes
its panel on `Escape` and on an outside click, which is correct, but
neither path returns focus to the trigger button — the open panel's
contents (an `OptionButton`) unmount and focus falls back to `<body>`.
A keyboard user who opens "Nutzung," arrows/tabs to an option, and hits
Escape to back out without choosing is dropped to the top of the
accessibility tree and has to tab back down through the whole page. This
is separate from the accessible-name/`aria-expanded` check already done by
hand — add `triggerRef.current?.focus()` in both the `Escape` and
outside-click handlers (well, only Escape needs it — an outside click
legitimately moves focus wherever the user clicked).

**2.3 — Verified working, worth recording:** no `div`/`span` is used as a
button anywhere in `app/` or `components/` (grepped every `onClick`) —
every interactive element is a real `<button>` or `<a>`. The `GermanyMap`
figure is `role="img"` with an `aria-label` summarizing the route, and the
per-stop minutes it doesn't expose to assistive tech are duplicated as a
real, readable `<ul>` next to the map (`ResultView.tsx:633-639`) — a screen
reader user doesn't lose that data, they just don't get it painted on the
SVG. `ChipGroup`'s single-select radiogroup (`ChipGroup.tsx:21-40`) is
correctly structured (`role="radiogroup"` wrapping real `role="radio"`
buttons with `aria-checked`), unlike 2.1 above.

## 4. Data honesty

**4.1 — Ranges render as ranges, consistently, and collapse safely.**
Verified in `lib/engine/parse.ts` (`formatDeSpan`/`formatRangeKm`) and
`components/ui/Num.tsx` (`NumSpan`): a span only collapses to a single
figure when `low === high`, which in practice only happens at the
theoretical floor of `computeRange` (`lib/engine/range.ts:102-103`, `low =
mid*0.88`, `high = mid*1.1` — these are never equal for `mid > 0`). Every
range-bearing figure in the app (`Autobahn-Reichweite`, charge-stop
minutes, total trip time) is rendered through this path and reads as a
true range with an en-dash, not a fake point value. This part of the
product's core claim holds up under inspection.

**4.2 — A single-point catalog figure sits next to a range in the new comparison table, with no note that it's a different kind of number.**
`lib/engine/types.ts` documents `highwayKwhPer100` as "kWh/100 km on
Autobahn at 15 °C / 130 km/h" — a fixed reference-condition manufacturer
spec, not adjusted for the reader's chosen month, speed, temperature or
occupancy. `components/advisor/ResultView.tsx:275-284` (the "Verbrauch
Autobahn" row, added with backlog #6's new always-visible table) prints
this raw catalog value with one decimal and no qualifier, directly below
the "Autobahn-Reichweite" row (`ResultView.tsx:236-244`) which *is* fully
adjusted for the reader's conditions and rendered as a range. A reader
comparing the two rows has no way to know one is a fixed lab reference and
the other is a live computation — and might reasonably (and wrongly)
back-calculate the range from the flat consumption figure and get a
different number. Should be: either compute and show the
condition-adjusted consumption here too, or add the same kind of
short parenthetical the app already uses elsewhere ("bei 15 °C, 130 km/h")
so the two rows don't read as the same category of fact.

**4.3 — The one number most likely to be checked against real life is marked UNVERIFIED in code, but that caveat never reaches the screen — and the confirmed problem is wider than one car.**
`lib/engine/charge.ts:1-23` is unusually candid in its own comment: the
`AVG_KW_10_80` table is "UNVERIFIED against manufacturer figures," and for
`skoda-elroq` specifically documents a known discrepancy — the table's
`mid` (100 kW) likely understates real average charge power (~115 kW),
meaning every displayed "ca. X Min" charge estimate for that car is
probably biased slow. *Mid-session, `engine` extended this comment*
(same file, dated 12.09.2026) with a second **confirmed**-conservative
entry (`kia-ev3`: table implies ~41 min for 10→80 %, Kia's own spec
implies ~29–31 min), a confirmed-fine entry (`byd-seal`, correctly matches
independent sources — explicitly "do not fix"), and a pattern observation
that five more entries (`bmw-ix1`, `cupra-born`, `renault-5`,
`opel-corsa`, `byd-dolphin`) cluster at the same suspicious 57–63 % of
peak-kW as the two confirmed-conservative cars, versus 69–75 % for the two
entries that look like real sourced data — i.e., most of the table looks
unsourced by its own internal pattern, not just the one car flagged at
audit start.

This is exactly the kind of thing rule 1 ("if a bound cannot be defended,
widen it") and rule 2 ("mark it where it can be corrected") should catch,
but — before and after the mid-session extension — the UNVERIFIED flag
lives only in a code comment. No per-car marker reaches `ResultView`'s
"ca. {mid} Min" (`ResultView.tsx:561-568`) or the comparison table's
"Laden extra" row; a `skoda-elroq` or `kia-ev3` row looks exactly as
confident on screen as a `byd-seal` row that's actually been checked. This
is already tracked as backlog #12/#13 (open) — flagging here specifically
that fixing the numbers is necessary but not sufficient: the product's own
rule says uncertainty this documented should be visible on screen, and
right now none of it is, for any car.

**4.4 — `data/**` now carries `meta.confidence` and a disclaimer — it did not at the start of this audit.**
At first read, `data/cars.de.json`, `data/climate-months.de.json`,
`data/routes.de.json`, and `lib/schema.ts` had no `meta.confidence` field
or anything structurally like it — only an `asOf` date per record, and one
prose `"note"` on the climate file. The task brief assumed `meta.confidence`
existed; at that point in the session, it didn't, and I flagged that
mismatch.

*Mid-session, `engine` added it to all three data files* and to
`lib/engine/types.ts` (`CatalogMeta`, with `asOf`/`disclaimer`/`confidence`,
plus a `notes` field on `Car`). Re-read after the change: `cars.de.json`
moved from a bare array to `{ meta, cars }` with a genuinely substantive
`meta.confidence` ("seed - unverified... four cars carry a specific notes
flag...") and a `meta.disclaimer` that calls out a real cross-check gap
(every one of the 15 cars implies a below-typical WLTP consumption when
back-calculated from `usableKwh`/`wltpKm`, 10.4–14.7 kWh/100 km against a
15–20 kWh/100 km class norm — flagged as possibly gross-vs-usable capacity
confusion, not silently accepted). `climate-months.de.json` and
`routes.de.json` each gained matching `disclaimer`/`confidence` fields.
`lib/engine/evaluate.ts` was updated in the same pass to read the new
`{meta, cars}` shape while still accepting the old bare-array shape (a
defensive backward-compat branch, not a breaking change). I verified this
lands correctly: `getCars()`'s output is unaffected either way.

Two things worth flagging even after the fix: (1) none of this new
`meta.confidence`/`disclaimer` text is rendered anywhere in the UI yet —
it's a data-layer improvement, not yet a reader-facing one, so the product
still doesn't visibly distinguish a `byd-seal` figure from a `skoda-elroq`
one (see 4.3); (2) the new `Car.notes` field exists in the type but I did
not find it populated on any of the four cars the top-level disclaimer
says carry one (`tesla-m3`, `tesla-my`, `mercedes-eqa`, `renault-5`) —
worth confirming with `engine` whether that's still in progress.

**4.5 — Assumptions are marked where they're set (`ControlBar`) and on price outliers; the per-value "Angenommen/Eingegeben" tag copy was dead, and `copy-guard` has now explicitly asked this audit to decide its fate.**
`lib/copy.ts:98-100` defines `assumedTag` ("Angenommen") and `enteredTag`
("Eingegeben") — at first read, grepped every `.tsx` file and found no
reference to either. *Mid-session, `copy-guard` added a comment right
above them* (own audit pass, same date) stating plainly that they're
unused, that `ControlBar` only marks an assumed value with italics +
color, and explicitly routing the decision to "the quality agent's
accessibility audit (backlog #2)" — this document.

Taking that hand-off: wire them up, not delete them. Finding 1.1 above is
that the italic/color-only marking fails contrast (3.24–3.57:1 against a
4.5:1 bar) — a visible text tag is exactly the non-color backup 1.1 already
recommends, and the copy already exists and is already locked/approved
(`lib/copy.ts` is copy-guard's file, so this text doesn't need inventing).
Concretely: render `COPY.assumedTag`/`COPY.enteredTag` as a small text
label next to each `ControlBar` value (or as its accessible name) instead
of, or in addition to, the italic styling. That closes 1.1 and 4.5 with
one change instead of two.

## What I could not verify

- **Screen-reader behavior with an actual AT** (NVDA/VoiceOver/JAWS). All
  screen-reader findings above are static analysis of ARIA semantics and
  the accessibility-tree/DOM, not a live AT pass. In particular I could not
  confirm how the standalone `role="radio"` (2.1) actually announces in a
  real screen reader, only that the markup is invalid per spec.
- **Live visual confirmation of 1.2's GermanyMap failure mode.** I
  confirmed the dark-silhouette-in-a-light-card problem live and confirmed
  the 1.24:1 ratio mathematically for a label on white, but I did not
  manage to force a live route/stop combination whose *label specifically*
  (not just the landmass) lands off the polygon before the dev server's
  live-editing made the tab unreliable to keep steering — treat 1.2's
  label-invisibility claim as a computed/geometric inference (a stop can
  fall outside the coarse `OUTLINE` polygon; when it does, this is the
  color math for that state), not a confirmed screenshot.
- **Print stylesheet / backlog #16.** `globals.css` has a `@media print`
  block that hides `.no-print` and forces black-on-white, but I did not
  print-preview any route — out of scope for this pass, flagging since
  data-honesty concerns (are ranges still ranges on paper?) would apply
  there too.
- **`/berater` under actual assistive tech at 390 px with VoiceOver's
  rotor / TalkBack**, specifically whether the `ControlBar`'s sticky
  positioning (`sm:sticky sm:top-0`, which is inactive below the `sm:`
  breakpoint per its own comment) creates any focus-order surprises on a
  real phone — I only checked layout and DOM order, not a physical device.
- **`compact` body-style / GLB coverage, Ladekurve numeric accuracy
  against real manufacturer tests** — explicitly owned by `showroom` and
  `engine` respectively per `CLAUDE.md`; only checked what's visible from
  the advisor/quality side (i.e., that the UNVERIFIED flag doesn't reach
  the screen, not whether the numbers themselves are now right).
- **Whether other agents' in-flight edits after this audit was written
  reintroduce or fix any of the above.** `ResultView.tsx` changed once
  under me (backlog #6 landing) and was re-audited against the new
  version; anything landing after this file was written was not re-checked.
